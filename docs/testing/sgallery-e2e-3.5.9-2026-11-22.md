# sGallery: свіже встановлення та браузерна перевірка Evolution CMS 3.5.9

Наступний прогін закрив E2E-02–E2E-04 у sGallery:
[виправлення та повторна перевірка](sgallery-e2e-fixes-2026-11-22.md).
Початкові результати нижче збережено як історичний зріз `d425a36`.

Перевірено 22.11.2026. Обробка зображень і штатні менеджерські сценарії
пройшли, але **безумовну готовність 1.9.0 до випуску не підтверджено**:
відкриті дві проблеми встановлення та збій upload у прямому вікні ресурсу.
Цей прогін уточнює попередній висновок про локальну релізну готовність.

## Код і середовище

- sGallery: `d425a36f113b2ce5a897386e62fed94ab787ab61`; локальний `main` і
  `origin/main` збігалися на початку перевірки. Production-файли встановлених
  пакетів звірено з поточним `src/`. Незакомічені зміни CI/документації збережено.
- Evolution CMS: тег `3.5.9`, commit `dc3d367b840132c79a15300a4f2397ee83b2b4c7`.
- sTask: `6355cf293422d43885d803cdd43637c0896f63cd`, із heartbeat API.
- Новий Docker volume: `sgallery-e2e-20261122-d425a36`. Попередній acceptance
  volume не використовувався як джерело сайтів, баз чи готових vendor-оточень.
- Три окремі установки та SQLite: `/lab/clean` без Spatie, `/lab/spatie` зі
  Spatie, `/lab/upgrade`, спочатку з sGallery 1.8.1 і Spatie, потім оновлена
  без image-пакетів Spatie зі збереженням кешу та п'яти старих завдань.
- CMS і старий пакет експортовано з Git. Vendor, який уже містив архів CMS,
  переміщено в окремі `shipped-*-vendor`; залежності отримано через Composer
  заново. Advisory-перевірки та `require-dev` CMS не вимикалися.
- Composer-залежності розв'язано на PHP 8.4.28 через E2E-01 нижче. Runtime:
  PHP 8.4.28, 8.5.13, стабільний 8.6.0; GD/Imagick/обидва/жодного. Imagick
  для 8.6 зібрано з раніше зафіксованого upstream commit.
- Код робочого checkout монтувався read-only. Сайти й бази інших проєктів
  не змінювалися. Коміти, push, теги та релізи не створювалися.

## Автоматичні перевірки

| Перевірка | Результат |
| --- | --- |
| Native: три PHP × чотири профілі драйверів | 219/219 runtime-прогонів |
| Spatie: повний `tests/ci/run-runtime.sh`, обидва драйвери, три PHP | 87/87 прогонів |
| Clean/upgrade × три PHP × чотири профілі драйверів | 24/24 клітинки, 882/882 твердження |
| GD без EXIF, зі Spatie й без нього, кожен PHP | 6/6 прогонів |

Перевірено геометрію, сучасні формати за доступними кодеками, анімацію,
прозорість, EXIF/ICC, watermarks, sharpening, quality/optimize, зміну джерела,
холодний і теплий кеш, старі descriptor, JSON-дедуплікацію та продовження
черги після контрольованої помилки. Без драйверів перевіряється повернення
оригіналу, а не успішне перетворення. Кодекові пропуски залишаються явними.

[JSON результатів](sgallery-e2e-3.5.9-2026-11-22.json) розрізняє
`accepted: true` для image/runtime-матриці та `release_gate_passed: false`
для повного випуску. Зелена матриця не приховує помилки Composer чи міграцій.

## Перевірки через браузер

Інтерактивні сценарії виконано Playwright у справжній оболонці менеджера з
`mainframe`, зі спостереженням DOM, HTTP-відповідей і зображень. Це локальна
браузерна перевірка агентом, без перевірки production або всіх браузерів.

| Установка | PHP | Результат штатного сценарію |
| --- | --- | --- |
| Чиста native | 8.6.0 | Пройшов |
| Чиста зі Spatie | 8.6.0 та 8.5.13 | Пройшов в обох runtime |
| Оновлена з 1.8.1, native | 8.6.0 та 8.4.28 | Пройшов в обох runtime |

Перевірено вхід Administrator, вкладку галереї, два upload, видимі мініатюри,
редагування текстів, збереження після перезавантаження, справжній drag-and-drop
зі збереженням порядку, відкриття/закриття viewer та frontend через публічний
`sGallery::collections()`/Builder API. Холодний і теплий frontend повертають
читабельні WebP з однаковими URL. Текст із `<тест>` зберігається як значення
атрибута. У штатних сценаріях Spatie/upgrade не було `pageerror`.

Штатна роль **Editor, ID 2**, без зміни її дозволів: читання відкритого ресурсу,
upload і видалення — успішні; приватний ресурс без document group і settings —
403. Фізичне видалення власного upload перевірено за станом каталогу та БД:
залишилися лише два збережені image-записи й два відповідні оригінали.

Додаткові HTTP-перевірки через справжню manager-сесію:

- PDF upload/delete та YouTube add/delete — 200 із `success: 1`.
- Реєстрація спільного бібліотечного зображення та видалення запису — 200;
  початковий бібліотечний файл зберіг SHA-256.
- Фальшивий PNG, шлях поза бібліотечним root, некоректний `itemType`, мова
  та `javascript:` у посиланні — 422. Непідтримані входи не виконувалися.
- POST без CSRF — 403. Анонімний GET повертає форму входу, без імен файлів
  галереї; його статус 200 не вважається доступом до даних.
- Налаштування sGallery збережено через штатну кнопку системної конфігурації:
  якість 89 пережила перезавантаження. Очищення кешу повернуло 200;
  власні оригінали збережені.

Повний вибір файла у вікні CMS file browser не проходився: перевірено реальний
endpoint реєстрації бібліотеки. Надсилання листів і зовнішнє YouTube-відтворення
не перевірялися. Аудит sCommerce залишається окремою задачею.

## Відкриті зауваження

### E2E-01 — Composer на чистому PHP 8.6, релізний бар'єр

`composer update --no-dev --no-scripts` на незміненому manifest Evolution 3.5.9
під PHP 8.6.0 не розв'язує `pestphp/pest:^4.7` та його ParaTest/PHPUnit.
Частина ParaTest допускає лише 8.4/8.5, новіші версії потребують несумісного
для цього Pest PHPUnit. `--no-dev` не вилучає ці обмеження з розв'язання.

Це обмеження root manifest CMS, не доказ збою NativeImage. Встановлення
залежностей на 8.4 та виконання встановленого runtime на 8.6 пройшли, але
не закривають сценарій прямого Composer-оновлення користувачем на 8.6.
Runtime CI тепер розв'язує fixture на 8.4, перемикає PHP й виконує
`composer check-platform-reqs --no-dev` перед тестами; upstream вимоги не обходяться.

Критерій закриття: чисте розв'язання і звичайне оновлення root CMS 3.5.9 на
8.6 без ігнорування platform/security constraints або погоджена й перевірена
політика встановлення, явно описана для користувачів. Код CMS не змінювався.
Початкові журнали: `%TEMP%/sgallery-e2e-{clean,spatie,upgrade}-install.log`.

### E2E-02 — історія міграцій після інсталятора, релізний бар'єр

Інсталятор CMS виконав три міграції sGallery та записав їх у
`migrations_install`. Звичайний `php artisan migrate --force` працює з
`migrations`, де цих записів немає. Перший `Schema::create()` у
`database/migrations/2022_05_15_185152_create_s_gallery_table.php:16`
отримує `table evo_s_galleries already exists`. Самі таблиці вже мають
`item_type`, `block` і залишаються працездатними.

Розділення таблиць задає `core/config/database/migrations.php:2` у CMS.
Сценарій відтворився на чистих установках і ще на 1.8.1 до оновлення;
це не встановлена регресія обробки зображень у 1.9. Не можна переносити
цей висновок на всі існуючі сайти з правильною історією `migrations`.
Помилка була в журналі навіть за exit code 0, тому одного shell-коду
завершення недостатньо для перевірки цих міграцій.

Критерій закриття: CLI/web установка → повторний звичайний migrate → оновлення
1.8.1 → повторний migrate проходять без помилок і втрати рядків/файлів,
з узгодженою історією. Не виправляти це видаленням існуючих таблиць.
Журнали: `%TEMP%/sgallery-e2e-*-install84.log`, `sgallery-e2e-*-finish.log`.

### E2E-03 — upload без оболонки менеджера, функціональний дефект

Відкрити `/manager/index.php?a=27&id=1` напряму в окремому вікні й вибрати
файл у галереї. `views/partials/scripts.blade.php:94` звертається до
`window.parent.document.getElementById('mainloader').classList`, хоча loader
відсутній. Відтворено `Cannot read properties of null (reading 'classList')`;
upload не доходить до HTTP. Аналогічна конструкція є для downloads на рядку 97.
У штатному manager shell upload працює. Дані не пошкоджено.

Критерій закриття: nullable loader не блокує завантаження в окремому документі;
обидва upload працюють і в shell, і без нього; loader ховається після успіху
та помилки. Потрібні браузерні регресії для двох контекстів.

### E2E-04 — текст успішного видалення, косметичний дефект

`src/Controllers/sGalleryController.php:346` повертає ключ
`sGallery::manager.deleted_successfully`, відсутній у наявних manager lexicon.
UI показує сам ключ. Видалення запису/власного файла проходить успішно;
спільний бібліотечний оригінал зберігається.

Критерій закриття: узгоджений наявний або доданий ключ у підтримуваних мовах;
toast після видалення містить читабельне повідомлення.

## Відтворення та доступ

Стенди залишено запущеними й прив'язаними тільки до loopback:

- Native / PHP 8.6: `http://127.0.0.1:18090/manager/`.
- Spatie / PHP 8.6: `http://127.0.0.1:18091/manager/`;
  той самий ізольований сайт на PHP 8.5: порт `18095`.
- Upgrade / PHP 8.6: `http://127.0.0.1:18092/manager/`;
  той самий ізольований сайт на PHP 8.4: порт `18094`.
- Frontend-проба: `/gallery-smoke.php` на кожному з цих портів.

Локальна папка harness:
`%TEMP%/sgallery-e2e-20261122-d425a36/`. Вона містить архіви, installer,
router, seeder, browser evidence та локальні доступи в `ACCESS.md`.
Ці допоміжні файли не змінюють пакет і не призначені для production.
Журнали основних наборів: `%TEMP%/sgallery-e2e-php{84,85,86}-{matrix,spatie}.log`.
Результати в volume: `/lab/results/summary-fresh-e2e.json` та окремі клітинки.

Повтор матриці: `sh /pkg/tests/acceptance/run-matrix.sh phpXX-<новий-label>`
у відповідному PHP-образі з цим volume, мережею `none` і read-only `/pkg`.
Підсумок: `php /pkg/tests/acceptance/summarize.php <label> <commit> 2026-11-22`.

Відомі попередження PHP 8.6 у Illuminate/Carbon/Composer та попередження про
майбутні методи SessionHandler у PHP 9.0 не виправлялися. HTTP працював із
`display_errors=0`, `log_errors=1`; повідомлення залишилися в Docker logs.
Перевірено SQLite й локальний PHP server з router, не MySQL/MariaDB, Apache/Nginx,
production-конфігурації, усі делегати кодеків або поведінку під навантаженням.

**Рекомендація:** перед випуском закрити E2E-01–E2E-03 або явно погодити
обмеження E2E-01; косметичний E2E-04 виправити разом із наступною перевіркою UI.
Код обробки та міграції пакета в цьому прогоні не виправлялися.
