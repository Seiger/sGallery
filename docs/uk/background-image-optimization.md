# Фонова оптимізація зображень

## Швидкі та повільні перетворення

sGallery обробляє зображення без кешу синхронно, якщо вистачає веббюджету пам’яті.
Типовий кооперативний
бюджет — п’ять секунд; його задає пакет, значення доступне через
`Seiger\sGallery\sGallery::optimizationBudgetSeconds()`. Готовий непорожній кеш
повертається одразу, порожні файли генеруються повторно.

Автоматичний підбір якості WebP зберігає 15 кандидатів:
`99, 97, 95, 93, 92, 91, 90, 89, 88, 87, 86, 85, 84, 82, 80`.
Вибирається перший кандидат, який вкладається в цільовий розмір, або останній,
якщо жоден не вклався. Явний `quality()` використовує одне задане значення.
Явна якість WebP може дорівнювати 100. Верхня межа типової якості з конфігурації становить 99.
Лише завершений непорожній WebP атомарно публікується з тимчасового файлу.

Бюджет перевіряється між перетвореннями та спробами кодування. Він не може
перервати вже запущений native encoder: перша обробка може перевищити п’ять
секунд або чинний PHP timeout. Позначка повільного перетворення зберігається
у спільному storage; наступні запити пропускають синхронну обробку.
Незавершені тимчасові файли не видаються як готові зображення.

## Необов’язкова інтеграція sTask

sTask виконує підтримувані перетворення через GD або Imagick.
Для анімованих GIF і WebP потрібен Imagick.

Пакет встановлюється незалежно. Передача в чергу потребує встановлених
runtime-класів sTask, API `heartbeat()` та актуального heartbeat runner-а.
Старі версії sTask без цього API не отримують відкладені завдання.

Воркер — `Seiger\sGallery\Workers\ImageOptimizationWorker`, ідентифікатор —
`sgallery.image-optimization`, дія — `optimize`. Перше відкладене завдання
реєструє відсутній воркер активним. Наявний вимкнений воркер не вмикається
автоматично: дозволь його виконання в менеджері sTask.

Після вичерпання бюджету фронт повертає URL оригіналу. Якщо sTask недоступний,
heartbeat прострочений або постановка в чергу не вдалася, оригінал залишається
доступним, а дороге перетворення не повторюється в кожному запиті. Уже відкрите
зображення не замінюється автоматично. Після успішної задачі воркер очищає
кеш сторінок і Blade views Evolution, щоб наступні запити використовували
готове зображення. Кеш похідних зображень не очищається.

## Великі зображення

sGallery оцінює пам’ять для оригіналу, похідного й проміжних зображень до
декодування. Фіксованої межі розмірів у пікселях немає. Вебзапит використовує
до половини вільного запасу PHP після резерву 16 МіБ для застосунку. Якщо PHP
має `memory_limit=-1`, початковий бюджет для оцінки становить 128 МіБ.
Коли перетворення виходить за межі цього запасу, sGallery передає його в sTask
і повертає URL оригіналу. Оригінал доступний і коли черга не приймає завдання.
Готові похідні віддаються з кешу.

## Ідентичність завдання та відновлення

Завдання зберігає шлях джерела, його розмір, час зміни та SHA-256 вмісту, визначений формат,
параметри перетворення та налаштування явної якості. Віддалені джерела не
потрапляють у чергу. Зміна джерела під час очікування відхиляє старе завдання.
Неблокувальний lock на завдання та дедуплікація sTask запобігають створенню
дублікатів. Після невдалого або завершеного завдання без придатного кешу
повторна постановка має паузу п’ять хвилин; активні завдання використовуються повторно.
Збережені скалярні параметри геометрії працюють в обох шляхах обробки.
Після нормалізації метаданих sTask воркер відновлює порядок параметрів watermark,
щоб готовий файл мав той самий ключ кешу, що й наступний запит frontend.
Зміну вмісту водяного знака перевіряють перед публікацією.

Ключ похідного містить повний шлях і версію джерела: заміна зі збереженими
розміром і mtime не повертає старі пікселі. Відбиток обчислюється потоковим
читанням, зокрема за кеш-влучання. Воркер звіряє версію до й після фінальної
публікації та перед успішним завершенням. За виявленої заміни біля публікації
щойно записаний застарілий кандидат прибирається; актуальна версія має інший
ключ. Джерело й раніше створені справні похідні зберігаються.
Старі двокомпонентні завдання size/mtime приймаються за збігу цих полів,
після чого фіксують поточний відбиток. Вони не можуть виявити заміну зі старими
статистичними даними до початку виконання, але обробляють актуальні байти
під актуальним ключем кешу.

Службові файли знаходяться в `storage/sgallery/optimization`. Storage має бути
спільним між релізами й доступним для запису фронтовому та CLI користувачам.

## Виконання завдань у sTask

Штатний runner sTask викликає воркер sGallery у своєму PHP-процесі. Воркеру
потрібен доступ на запис до кешу зображень. Перед обробкою він повторно звіряє
оцінку пам’яті з `memory_limit` runner-а. За значення `-1` початковий бюджет
оцінки становить 512 МіБ.

Після перевірки готове зображення публікується атомарним перейменуванням файла.
sTask фіксує оброблювані помилки й переходить до наступного завдання. Фатальна
помилка, яка завершує PHP-процес runner-а, може перервати поточний запуск.
Кеш сторінок очищається після успішного завдання.

## Перевірка

Запусти інтеграційні тести з Composer runtime установленого Evolution, sTask
із heartbeat API, підтримкою GD/WebP та SQLite:

```sh
SGALLERY_AUTOLOAD=/path/to/site/core/vendor/autoload.php php tests/image-optimization.php
php tests/optional-stask.php
```
